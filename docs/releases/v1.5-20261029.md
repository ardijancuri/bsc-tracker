# v1.5 — OpenFour artwork and reliable image scheduling

Release tag: `v1.5`. Package version: `1.5.0`.

OpenFour and ordinary Four.Meme token images previously went through the Genius
lookup and remained missing. The optional image worker now selects Flap,
Four.Meme or bounded Four.Meme/Genius discovery from the recorded launch source.
The Four.Meme lookup requires its first-party record to match the full contract
address and BSC network. It consumes only that token's image field, requests JSON
explicitly and normalizes the result to bounded cached WebP.

Creator avatars, template banners, nested metadata, symbol matches and another
chain's record cannot supply token artwork. Public-address checks, private-DNS
blocking, manual redirects, byte/pixel limits, leases, cooldowns and the
public-traded-token filter remain enforced. No provider financial values are
used by this image path.

The image scheduler checks current capture/decoding health and the recent pending
queue. Old historical accounting-repair checkpoints no longer prevent optional
artwork from loading. Fresh capture and decoding retain priority; accounting
completeness, unknown costs, P&L and replay approval rules are unchanged.

This release includes all previously committed v1.4 updates, including stored
rolling P&L, explicit estimated token results and estimated replay exports. It
adds no database tables, columns, historical imports or financial reprojection.

## Validation

- The image/scheduling patch passed 5,392 tests with two skipped. The cache-lock
  test initially hit a Windows temporary-file EPERM; its focused rerun and final
  complete run passed. Both TypeScript projects and the production build passed.
- Real 4Broker and OpenID images were fetched from their exact Four.Meme records,
  normalized and verified through live Kollens image endpoints. Existing Genius
  DEGENIUS and DOG images remained valid.
- All 27 publicly tracked tokens recorded with the Four.Meme launch protocol had
  cached artwork after recovery. The canonical-EVM OpenFour examples were also
  recovered without changing their launch classification.
- Before/after preservation verified 30,507 original financial records, 579,272
  known financial fields, all 228 accounting scopes and all 21 account/settings
  table digests. Only normal 72-hour temporary-evidence expiry occurred.

## Release procedure

Build from this exact committed revision, bind source and runtime checksums to
the release, and preserve the existing production database, mounts, environment
and championship scheduler. Keep the existing Compose project name so accounts,
settings and volumes are reused. Do not initialize or reset a database, rerun
accounting-policy projections, reimport financial history or send test messages.

The existing startup schema check takes exclusive relation locks. Drain the API
and worker together during the bounded handoff, start the worker and confirm new
capture progress, then start the API. Do not start a duplicate preview API against
busy production tables or repeatedly restart a worker under active page queries.
Verify a single collector, fresh post-handoff capture, public endpoints and both
runtime release identities. Retain preservation reports and compare original
financial and account records after the switch.

Missing upstream artwork remains a bounded optional retry. This release does not
claim to recover missing historical monetary inputs or manufacture chart data.
