# kollens

Public, read-only BNB Smart Chain KOL trade tracker. The 226 wallets and X handles in `server/roster.json` were normalized from the user-supplied GMGN KOL CSV. The app tracks exactly this roster and needs no GMGN API key. Names, handles, and wallet addresses are data supplied by the roster; kollens does not independently verify identity ownership.

## Brand assets

The approved source logo is preserved in `branding/kollens-approved/source.svg`. The white/yellow variants in `public/kollens-logo-{white,yellow}.svg` and `public/kollens-icon-{white,yellow}.svg` are the build's canonical assets. The app's header and footer both use the all-white logo directly. `npm run brand:export` regenerates only the favicons, touch icon, trade replay artwork and native-path fallbacks, and the website's social preview. Artwork URLs are versioned to avoid stale browser and social caches. The export runs before every production build. Final X assets are listed in `branding/README.md`.

## Pages

- `/trades` — observed swaps initiated by tracked wallets, with filters and BscScan links
- `/tokens` — tokens traded by tracked wallets, ordered by recent activity
- `/leaderboard` — wallets active in the last 24 hours, ranked by realized USD profit from positions bought and sold within that rolling window
- `/kol/:address` — wallet profile, X link, paginated trades from the last 24 hours, tokens, and 24-hour tracked P&L

The worker follows new BSC blocks via WebSocket and queries the local HTTP RPC for ERC-20 transfers, transactions, and receipts. It waits six blocks, stores trades once, and rescans after short reorganizations. BNB/USD comes from the [Chainlink BNB/USD feed on BSC](https://data.chain.link/feeds/bsc/mainnet/bnb-usd), read through the local node. BNB-quoted swaps are valued at the price reported near their block; stablecoin-quoted swaps use the quoted amount. Ambiguous interactions remain unpriced.

The public leaderboard uses a continuously moving 24-hour window and FIFO cost basis from observed, valued purchases made within that window. Sales without enough priced purchases in the window are excluded; complete sales still contribute, with an asterisk indicating excluded sales. A dash means sales occurred but none could be fully valued, while no sales means $0 realized. Auxiliary dividend trackers and ambiguous quote values duplicated across multiple assets in one transaction do not inflate P&L. These are tracked estimates: unobserved transfers, incomplete indexing, trading fees and gas can affect actual wallet profit. The worker verifies previously imported trades against historical BSC receipts through `BSC_HISTORICAL_RPC_HTTP` (defaulting to the official public endpoint); unverified imports do not affect P&L. New roster wallets begin accumulating trades when the worker first sees them. Token prices are the last observed swap price, not a market quote. The site has no wallet connection or trading action.

The token tracker includes recognized meme launchpad contracts and known meme coins, excluding quote assets, LP tokens and dividend trackers. Its initial one-hour window uses on-chain trade timestamps. Logos are validated by decoding their image bytes, cached locally and served through `/api/token-image/:address` with a content version. IPFS images retry independent gateways; oversized animation uses a compact still frame. Coins with unavailable artwork keep a readable initial while background retries continue.

## Run

Use Node.js 22+, PostgreSQL 17, and a BSC node with HTTP and WebSocket RPC. Copy `.env.example` to a private `.env`, set `BSCAN_DB_PASSWORD`, and run `docker compose up -d --build` on the VPS. The API binds to loopback port 3300; PostgreSQL binds to loopback port 5434. RPC access remains private. `GET /api/health` checks the API and database. `GET /api/overview` reports roster and data freshness.

For local development, configure a private `.env` with `DATABASE_URL` and optional `GMGN_CHART_API_KEY`, run `npm install`, then `npm run dev` and `npm run dev:api`. The API reads the local `.env` automatically. The worker runs with `npm run dev:worker`. Use `npm run check` and `npm test` to verify the code.

## KOL images

`node scripts/fetch-kol-avatars.mjs` reads the roster's X handles, saves publicly available profile images in `public/kol-avatars/`, and records their source URLs in `server/x-avatars.json`. It skips images already saved; pass `--refresh` to fetch current photos again. Rebuild the app and worker after updating the manifest. Wallets with no retrievable X photo show their initial instead of an unrelated image. The worker retries missing public X photos weekly.

## Leaderboard P&L

The public 24-hour leaderboard is calculated from verified indexed trades every two minutes and stores period `1d` with its rolling window start. Optional `GMGN_API_KEY` still populates separate legacy 7-day and 30-day snapshots through the official batch wallet profits API; these are not used for the public ranking. Never commit the API key.

Token cards on KOL profiles and their trade modals display estimated total profit for open positions and realized P&L for closed positions, including marked transfer-out gains and fees. They request `GET /api/kols/:wallet/tokens/:token/activity?pnl=true`; the separate `realizedAccounting` result must reconcile complete wallet movements, the canonical balance, and GMGN accounting for that exact pair. Open-position marks carry their own price timestamp and expire independently of historical costs. Indexed buy/sell amounts remain available separately. Unknown transfer costs or fees are never assigned zero or replaced with a partial FIFO total. The existing GMGN key can verify a final position aggregate when the wallet appears in the available trader results, or derive estimates from complete fee-accounted activity; unsupported positions show an unavailable explanation.

Verified historical realized totals are cached for ten minutes and reused only after fresh canonical inventory verification confirms unchanged movements, balances, and valuation inputs. New transfers and trades invalidate the result. Both profile and replay requests reuse complete matching transaction history within a three-minute verification window; reported position quotes still refresh after fifteen seconds. Shared work promotes to foreground priority when a replay joins. Bounded ranking lookups remember missing-wallet results and the last successful ranking so quota waits do not repeatedly restart the same search. Offscreen cards defer P&L requests, and background card work pauses while a trade modal is open. Verified replay accounting also warms the profile cache. Derived estimates retry for a reported total without replacing an already verified total with a lower-quality result.

Replay profit follows the verified cash-flow identity: sales plus marked transfer-out income plus current held value minus fee-inclusive cost. It does not require a known realized/unrealized split to display a known total. For native BNB swaps routed through an intermediate pool token, the same transaction's GMGN native-gas/USD pair supplies native FX; the pool token quantity is never treated as BNB. Exact reported ending totals remain separate from historical estimates. Replay preparation resumes paced transient failures automatically, requires genuine market observations through the current valuation window, and never fills a missing day of history with a current quote. Unsupported WebCodecs configurations may use compatible MediaRecorder capture before encoding begins.

## Radar, watchlists, holdings and launches

The app supports English and Simplified Chinese. The language selector is on the right side of the header, with a compact control on mobile; the selection is saved in browser local storage and applies across pages, accessible labels, dates and number formatting. Token/KOL identities and on-chain data remain unchanged. UI copy is maintained in `src/zh-CN.ts`; translations do not require external requests.

Chinese token detail pages show a short English name beneath the original title. `/api/tokens/:address/translation` translates the Chinese full name, or symbol when a Chinese full name is unavailable. Successful translations persist by normalized source text, so duplicate token names share a cache and renamed tokens use a new entry. English/Japanese/Korean names are skipped. MyMemory receives only public token names and the language pair, never browser cookies or wallet data. Its [documented API](https://mymemory.translated.net/doc/spec.php) allows 500-byte inputs; requests share a persistent 5,000-character daily anonymous allowance, with two concurrent lookups and an hour between failed attempts. A provider outage or exhausted allowance exposes a compact Google Translate link rather than an incorrect name. These are automatic translations, not official token renames.

`/trades?view=radar` shows 20 signals at a time with expandable transaction evidence. `/trades?view=watchlist` groups followed KOLs/tokens and their signals. Filters are saved in the same browser: 5/10/30 minute buying windows, 2–10 distinct buyers, categories. A new filter profile backfills the last day without alerting. Live triggers use confirmed chain order and a ten-minute cooldown. Imported activity is silent; corrected signals remain visible after a reorganization.

A secure HttpOnly, SameSite=Strict cookie identifies an anonymous watchlist; the server stores its hash. No wallet connection or account signup is needed. Follow stars appear on profiles, token cards and leaderboard rows. Clearing Watchlist deletes its session and preferences. Cross-device recovery is deferred.

Holding badges use confirmed `balanceOf` snapshots and tracked-wallet ERC-20 movements, including transactions initiated by other wallets. Initial positive balances establish Holding; later labels require matching movement evidence. Zero without a known sale, mixed/unexplained changes, RPC failures and snapshots more than five minutes old show Unknown. Exact quantities are available on expansion. Holdings do not alter the rolling 24-hour P&L calculation. Reconciliation uses four concurrent balance RPC calls and prioritizes new movements and watched positions.

`/tokens?view=launches` covers Four.meme classic V1/V2 and Flap tokens already traded by the roster. Membership comes from Helper3/Portal state and official events; address suffixes do not establish launch membership. Progress uses each token's on-chain target; 90% starts Near graduation. Initial discovery of an already-graduated token is silent. Dates come from contract timestamps or indexed events and remain unavailable when history is missing. Flap Infinity uses its separate pool ID, never a vault as a pair. DEX Screener observations keep their timestamp and explicitly recorded first liquidity baseline. OpenFour and other launch protocols are unavailable in this release.

The migration is in `server/intelligenceSchema.ts`. Collection, signal evidence, movement snapshots, launch observations persist in PostgreSQL. Reorg handling marks signals corrected and removes affected observations. Independent collector loops keep launch RPC retries from delaying Radar. `GET /api/intelligence/health` reports processing lag, stale positions; `/api/overview` includes chain lag.

### Token market charts

Main token pages request `history=full` independently of candle resolution. The newest candles render first; visible pages then request earlier real candles with `before=<oldest Unix seconds>` until the provider's available history is exhausted. Completed and in-progress history is cached for reuse. Earlier pages use lower priority than new main-chart requests, respect provider cooldowns, and stop loading when the page is hidden or unmounted. The chart fits all loaded candles on initial display and expands as earlier history arrives; normal quote refreshes retain the user's zoom and pan. Missing provider history is labelled rather than filled with invented candles. Timeframe buttons use compact text-only selection in token pages and trade popups.

`GET /api/tokens/:address/chart?period=24h|7d|30d` serves genuine USD market history independently of KOL trades. The default provider is [CoinMarketCap's documented keyless DEX API](https://coinmarketcap.com/api/documentation/pro-api-reference/ohlcv/), requested directly by BSC token address. Only latest candles are requested: explicit `from`/`to` history needs a paid subscription. `CMC_CHART_MAX_CANDLES` optionally caps fetched bars at 1–1000. A private server-only `GMGN_CHART_API_KEY` selects official GMGN history first and reserves its allowance for app charts. The legacy `GMGN_API_KEY` remains a fallback and also enables worker profit snapshots. Cold charts fall back to CoinMarketCap and then GeckoTerminal; verified pool/token relationships protect Gecko requests from paired-asset mistakes. The public tracker needs no GMGN key.

Token pages and KOL trade popups open at 1m by default; preloading uses the same interval, and loading trade history preserves the selected interval. Token pages use `?interval=1m|5m|1h|4h|1d` and native candlestick charts with crosshair, zoom and pan. Every candle uses genuine OHLC values and its actual timestamp. The market-cap axis uses current on-chain token supply, returned as `marketCapSupply` and `supplyCheckedAt` when checked within two days (decimals 0–36); historical supply changes are not modelled. Missing or expired supply triggers a coalesced on-demand ERC-20 read independently of worker pricing, concurrently with candle loading. Node calls have a three-second deadline, responses wait at most 250ms for supply, and selected charts retry pending supply in one second; background sparklines retry in three seconds. Successful raw supply and decimals persist to the database; failures use a 30-second cooldown. Loading supply is distinguished from missing market-cap data. Recent-history requests used by preloads, watchlists and trade popups retain their bounded windows: 1m requests up to 1,000 recent minute candles and refreshes at most every 30 seconds; 5m requests up to 24 hours, 1h 30 days, 4h 90 days, and 1d 180 days, subject to provider coverage and limits. Main token pages load earlier history independently of these windows. Partial history is labelled. Watchlist sparklines use candle closes, and the KOL trade modal retains its candle renderer and trade markers. CoinMarketCap's volume denomination is unspecified, so its volume is not labelled USD or drawn as a dollar-volume histogram. GMGN's current BSC OpenAPI uses `volume` for USD turnover and `amount` for token units. Its documentation contains conflicting descriptions; live BSC response values were checked against candle prices before enabling the histogram. Older GMGN caches retain prices but hide unverified volume until refreshed. Token activity statistics stay on 24h regardless of chart interval.

Requests are coalesced and paced through provider-specific shared PostgreSQL budgets. CoinMarketCap's anonymous numerical allowance is undocumented; its requests use conservative 6.5-second pacing, bounded priority queues and at least 60-second exponential backoff on rate limits or outages. GeckoTerminal shares its 6.5-second budget with website and worker-logo requests. Optional GMGN uses a shared account budget across chart, replay and profit requests. Selected charts take priority over hover prefetches, queued sparklines and metadata. Provider queues reserve capacity for main charts even when background queues fill; coalesced prefetch jobs promote when opened. Visible background charts pause while the main chart is waiting for usable data, and preloads skip while it loads. Provider cooldowns apply across processes and their remaining duration is sent to clients; no provider is assumed unlimited. The 24-hour/5m chart refreshes at most once every two minutes per token; background watchlist requests reuse it for five minutes. Identical 5m/24h requests share cached data and jobs; weekly, monthly and 1h views share one hourly fetch, clipped to the requested period. Gecko pool discovery is coalesced across intervals and cached for ten minutes. Finer real cached candles can be grouped into coarser UTC buckets while those intervals load, with limited history labelled; coarse bars are never split into invented prices. Cold interactive chart responses wait up to eight seconds for the existing provider job to complete, eliminating an unnecessary polling round trip for normal provider responses; cached charts return immediately and background responses retain their one-second wait. Chart responses persist in memory and `.cache/token-charts`, backed by the Compose volume; atomic disk writes happen after publishing fresh candles. Cached history survives provider failures without continually spending fallback allowance. Loading responses are not HTTP-cached; the browser coalesces duplicate requests, aborts stalled requests after 12 seconds, polls selected queued charts every second (background sparklines every three seconds) and honours the remaining provider cooldown. Refreshes stop in hidden tabs, and offscreen sparklines stop polling. Sparklines may fall back to labelled recorded prices or the latest quote; full charts distinguish waiting, cooldowns and provider failures from genuine absence of history, retain valid cached candles, and offer a cooldown-aware retry button. Invalid or duplicate bars are filtered before rendering. The header banner uses weekly history and weekly percentage changes independently of watchlist table tabs.

### Validation

Chart requests begin on deliberate hover, keyboard focus or pointer-down on token links and interval buttons, and alongside token details. Trade cards also warm the lazy modal code. Equivalent 24h/5m and 30d/1h browser caches supply an immediate initial chart (with monthly history clipped for weekly views), and shared subscribers update as soon as a preload completes. The browser retains the last twelve charts with verified, unexpired supply in session storage, so reopening or reloading can display real cached history immediately while fresh data loads. Incoming candles with temporarily missing supply can reuse that token's timestamped supply across intervals, but never extend its two-day validity. Restricted browser storage leaves the memory cache usable.

Production HTML revalidates on each navigation; fingerprinted `/assets/` files have immutable caching. Missing asset paths return an uncached 404 instead of the SPA shell. Compose mounts `bscan_frontendassets` at `FRONTEND_ASSET_CACHE_DIR`; startup retains the current release's fingerprinted assets and removes omitted files older than seven days. Keep this volume across deployments. When first enabling it, seed fingerprinted assets from the currently running app before replacing its container so existing tabs can still open lazy trade details. Later releases retain these files automatically. A popup import failure checks the current HTML entry: if the build changed, it reloads once and restores the selected KOL/token; otherwise a closeable error dialog offers a manual reload. Hover preload failures never reload the page.

Live data hooks share one `/api/stream` connection per tab. Transport errors close the failed connection and retry after 2, 4, 8, 16, 32, then at most 60 seconds. The connection pauses offline and in hidden tabs; existing polling remains the fallback. These changes reduce duplicate connections and retry noise; they do not change the reverse proxy's HTTP/3 configuration.

Run `npm run check`, `npm test`, and `npm run build`. For database-backed validation, create a disposable PostgreSQL database named `bscan_intelligence_test` or `bscan_intelligence_test_<digits>` and set its private `DATABASE_URL`, then run `npm run test:integration`. The runner refuses other database names, mocks RPC/DEX Screener, and tests migrations, profile backfills, isolation, movements, stale/failed checks, launch milestones, pool IDs and reorgs. `INTELLIGENCE_PREVIEW_FIXTURES=1` leaves synthetic fixtures for isolated desktop/mobile QA; never use them in production.
